# monitoring.md — наблюдаемость в эксплуатации

Мониторинг устроен так, чтобы отвечать на три вопроса: система **работает**
(технически), **не деградирует** (ML), **решает исходную задачу** (продукт).

## Технические метрики

- Latency горячего пути: p50 / p95 / p99; **алерт при p95 > 500 мс** (нарушение
  бюджета классификации/маршрутизации).
- Latency и доступность LLM API; доля таймаутов; глубина очереди холодного пути.
- Пропускная способность, доля ошибок по компонентам, срабатывания circuit breaker.
- Health хранилищ (векторная БД, KB, кэш), hit-rate кэша LLM.

## ML-метрики

- Распределение уверенности классификатора; доля abstain (маршрутизации по низкой
  уверенности).
- Per-class precision/recall по **выборочной ручной разметке** потока (проверяем
  реальную точность на проде, а не только офлайн); отдельный контроль recall
  рискованного класса.
- Retrieval: recall@k / MRR на контрольных парах; доля запросов «нет опоры в KB».
- Доли действий: auto-close / suggest / escalate; доля принятия черновиков и
  edit distance операторов (качество генерации).

## Продуктовые / бизнес-метрики

- **North Star:** доля закрытых без оператора при неухудшении CSAT.
- Guardrails: reopen rate (общий и **отдельно на автозакрытых**), CSAT (общий и на
  автозакрытых), SLA breach rate первого ответа, время обработки (AHT).
- Стоимость обработки одного тикета (операторная + LLM).

## Стартовые алерты

- p95 горячего пути > 500 мс.
- Всплеск доли эскалаций или доли «нет опоры в KB» (сигнал сдвига потока/деградации).
- reopen rate на автозакрытых > 1.5–2× базового ИЛИ CSAT на автозакрытых ниже
  базового > 0.3 → **автоматическое сужение allowlist / откат автозакрытия**.
- Рост ошибок LLM API / доля таймаутов выше порога → включение деградации.
- Дневная стоимость LLM выше бюджета → алерт + circuit breaker (см. ниже).

## Отличить деградацию модели от изменения входящего потока

Ключевая ловушка: метрики качества упали — это модель хуже или вход изменился?

- Отдельно мониторим **распределение входа** (микс тем, каналов, языков, длины,
  объём). Скачок объёма/микса — признак инцидента или сдвига потока, а не
  деградации модели.
- Сопоставляем: качество упало **при стабильном входе** → деградация модели;
  качество упало **вместе со сдвигом входа** → сдвиг данных (новая тема, новый
  тип обращений), реакция другая — дообучение/расширение KB, а не откат модели.
- Детектор инцидентов по всплеску объёма (10–20k/10 мин) переводит систему в
  режим дедупликации и приоритезации.

## Мониторинг стоимости LLM

- Токены и стоимость на вызов и на тикет; дневной/недельный расход vs бюджет.
- Hit-rate кэша (падение кэша = рост стоимости); доля ретраев (циклы = утечка
  бюджета).
- **Circuit breaker по стоимости:** при превышении бюджета — приоритет suggest над
  автозакрытием, агрессивнее кэш, часть кандидатов на оператора.

## Как отслеживается, что решается реальная исходная задача

Автоматизация ради метрики автоматизации опасна. Поэтому замыкаем на исход:

- Автозакрытые тикеты **остаются закрытыми** (низкий reopen на них) — иначе
  «закрытие» фиктивно и лишь маскирует нерешённую проблему.
- CSAT и время первого ответа на автоматизированном сегменте не хуже ручного.
- Доля жалоб/эскалаций после автоответа. Регулярная выборочная ручная проверка
  автозакрытых ответов на корректность.
